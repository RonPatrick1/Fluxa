# Bose battery voice-prompt research

## Confirmed devices

| Speaker | Product | Product ID | Firmware |
| --- | --- | --- | --- |
| Elizabeth's Bose | SoundLink Max (`Edelman`) | `0x094F`, variant 1 | `8.2.16+g259c916` |
| Freddie's Bose | SoundLink Flex (Gen 2, `Mathers`) | `0xBC61`, variant 11 | `4.11.26+g1b552db` |

Freddie has not received any setting or firmware writes during this research.

## Battery-prompt packet

The current Bose app's
`SettingsVoicePromptsResponse` and `SettingsVoicePromptsSetGetPacket` classes
confirm the packet layout. It is BMAP Settings block `0x01`, function `0x03`.

The response payload is either five bytes (legacy response) or seven bytes:

| Byte | Meaning |
| --- | --- |
| 0 bits 0-4 | voice language ID |
| 0 bit 5 | global voice prompts enabled |
| 0 bit 6 | default language |
| 0 bit 7 | user may toggle global prompts |
| 1-4 | supported-language bit mask, big-endian |
| 5 bit 0 | battery-level prompt supported |
| 6 bit 0 | battery-level prompt enabled |

The app changes the battery option with a two-byte SetGet payload. The first
byte contains the existing global enable bit and language. The second byte is
`0x01` for battery prompts on or `0x00` for off.

Live responses:

```text
Freddie:   e1 0001815e 01 01 -> supported, enabled
Elizabeth: 41 00008102 00 00 -> unsupported, disabled
```

On August 3, 2026, the old SetGet request was sent once to Elizabeth with her
global voice setting and language preserved. Firmware 8.2.16 returned the same
`unsupported, disabled` response. This rules out a hidden setting-only fix.

Elizabeth's firmware-update block then reported protocol `1.2.0`, state `Idle`,
zero staged bytes, and staged version `0.0.0`. Only read-only Get operations
were used; no firmware transfer was initialized.

## What changed in firmware

Bose lists SoundLink Max firmware 8.2.16 as a March 3, 2026 release with
“Updated voice prompts and tones.” The older 4.12.18 image contains Bose's
on-device TTS engine, voice packs, number-prompt playback, and power-on battery
prompt code. The battery announcement is generated by the speaker firmware;
it is not an audio file supplied by the phone app.

Firmware history:

https://support.bose.co.uk/article/soundlink-max-portable-speaker-software-and-firmware-versions

## Model-correct rollback candidate

The older, Bose-hosted SoundLink Max image is still available:

```text
Version:  4.12.18+g912e75d
File:     edelman_encrypted_prod_4.12.18.bin
URL:      https://downloads-dev.bose.com/ced/edelman/edelman_encrypted_prod_4.12.18.bin
Length:   5,681,752 bytes
CRC32:    0xE7EEED5E
SHA-256:  4120331f8f1e9ff1fb122a832efec4087323c4904bc5269c1ea127bb10055a8e
```

`edelman-rollback-candidate.xml` describes this exact product and image. Its
advertised version is deliberately higher than 8.2.16 so an updater would
offer it; the signed image itself remains Bose's unmodified 4.12.18 build.

This is not yet a safe one-click rollback. The speaker may enforce an
anti-rollback version check or may be left in recovery mode if validation or
installation fails. Do not transfer or run the image without explicit consent,
continuous power, and a tested recovery path.

Do not use the third-party `indexflex2.xml` manifest for Elizabeth. It maps
SoundLink Max product ID `0x094F` to `Mathers` (Flex Gen 2) firmware. Freddie's
actual Flex Gen 2 product ID is `0xBC61`; sending Mathers firmware to Elizabeth
would be a wrong-model flash.

## Update transport decoded from the app

The mobile app uses BMAP function block `0x03` for firmware updates:

| Function | Operation |
| --- | --- |
| `0x00` | function-block information (read-only) |
| `0x01` | transfer state (read-only) |
| `0x02` | initialize transfer |
| `0x03` | transfer data |
| `0x04` | synchronize/resume |
| `0x05` | validate image using reversed CRC32 |
| `0x06` | run the validated update |
| `0x07` | reset update state |
| `0x08` | transfer data with sequence number |

The app passes the manifest's version string during initialization, then sends
the image, validates it, and separately requests installation. That separation
makes a future guarded updater possible, but initialization and later steps are
still firmware-writing operations.
